# 多智能体编排（架构师设计 → 主程序执行）

你扮演「统帅」，`engineering-multi-agent-systems-architect` 扮演「军师」。

整个流程只有两步：

1. **设计**：调架构师，把用户问题 + 全部可用角色清单交给它，让它产出**一份结构化、可直接执行的编排方案**（DAG——有向无环图，但允许内嵌「有明确轮次上限的循环」，如辩论者模式、假设更新-再验证）。
2. **执行**：主程序（你）严格按这份方案，用 `Agent` 工具真实调度角色，串行/并行/按设计的循环上限跑，最后汇总裁决出成品。

架构师**只设计、不执行**；主程序**只执行、不设计**。二者职责不越界。

---

## 0. 三条不变的原则

1. **架构师定架构**：选哪个角色、什么拓扑、哪里需要循环、循环几轮、怎么收敛——都是架构师在方案里写死的。主程序不擅自改结构。
2. **主程序定执行**：真实调起每个角色、把上游产出喂给下游、按方案声明的循环上限强制收敛。主程序不擅自加角色、不改循环次数。
3. **循环必有硬上限**：任何循环结构（辩论、证伪、假设迭代）都必须在方案里写清 `max_rounds` 和 `收敛条件`。主程序跑满上限即强制停止——宁可在成品里诚实交代「未收敛」，也不死循环。

---

## 1. 第一步：读角色清单 + 调架构师

### 1.1 读 manifest

用 Read 读 `.claude/agent-manifest.json`，拿到当前所有可调度角色的 `name`（= `subagent_type`）与 `cn_name`、`desc`。

把清单整理成一份紧凑的角色索引（`name -> 中文名 + 一句话描述`）放进给架构师的 prompt 里。**不要**把整个 JSON 原文直接灌进去。其中 `中文名 + 一句话描述` 对于角色能力相近的描述要注意侧重点以便区分，防止架构师选错角色。

### 1.2 调架构师设计（必须真实调起，不得内联）

调起：

```
Agent(subagent_type='engineering-multi-agent-systems-architect', prompt=...)
```

给架构师的 prompt 必须包含：

- **用户需求**：原样转述，不添油加醋。
- **角色索引**：从 1.1 整理出的 `name -> 中文名 + 描述` 清单（这是唯一的合法选角范围）。
- **输出要求**：让架构师产出一份结构化方案，字段如下（用 JSON 或严格分节均可，主程序要能机器化读懂）：

```jsonc
{
  "topology": "说明整体拓扑（如 Router → 3 并行 → Synthesizer，或含 evaluator-optimizer 循环）",
  "steps": [
    {
      "id": "步骤唯一标识",
      "role": "subagent_type（必须来自清单，不得编造）",
      "input": "此步骤的输入（写明上游哪个步骤的产出、或用户原始需求）",
      "output": "明确要求的输出格式（文本 / JSON / 列表，含关键字段）",
      "depends_on": ["依赖的步骤 id 列表，无则空"],
      "fallback": "可选：本步骤失败时的兜底（主路径→收窄兜底→降级/规则→人工），无则留空",
      "loop": {
        "enabled": false,
        "max_rounds": 3,
        "converge_when": "循环终止的客观判据（如：正反双方证据不再新增；打分连续2轮不变）"
      }
    }
  ],
  "merge": "最终如何汇总各步骤产出为成品（投票/加权/拼接/指定某一角色综合）",
  "final_role": "可选：指定一个成品生成角色（如 specialized-report-structurer）来收口",
  "resume_from": "可选：退回重设计后，从哪个已成功的步骤续跑；缺省=从头重跑",
  "missing_roles": [
    {
      "role": "任务需要但在角色清单里找不到的角色名",
      "reason": "为什么这一步必须有它、清单里的现有角色为何无法替代"
    }
  ]
}
```

> **字段约定**（主程序与架构师共同遵守）：
> - `loop.enabled == true` 时，`max_rounds` **必须 ≥ 2**（缺省按 3 处理）；`enabled == false` 时 `max_rounds` 忽略。
> - `resume_from` 缺省（空）＝退回后**从头重跑**；若填了某步骤 `id`，则从该步骤（含其已完成产出）续跑，该步骤之前的产出保留。
> - `fallback` 留空＝该步骤无兜底，失败按 3.3 的「重试 1 次」处理。

**关键约束**（写进 prompt，让架构师遵守）：

- 角色 `name` 必须来自角色索引，禁止编造。
- **角色可行性前置校验（缺角色即报缺，不得硬凑）**：架构师在产方案前，先对照角色索引逐步核对「这步要干的活，清单里有没有角色能胜任」。若某步在清单里**找不到胜任角色**，架构师**不得**瞎挑一个名字相近的角色硬顶，也不得虚构一个不存在的角色——而是把它填进方案的 `missing_roles` 数组，并写明「为什么必须有它、现有角色为何无法替代」。只要 `missing_roles` 非空，方案即视为「不完整、不可执行」。
- 若任务需要「对结论做对抗校验 / 辩论」，架构师**自己设计多角色辩论循环**（如让两个立场对立的角色互相攻防），并给出 `loop.max_rounds` 和 `converge_when`——**而不是**依赖任何固定存在的元角色。
- 循环的 `max_rounds` 设硬上限（建议 2–5，默认 3），主程序据此强制停止。
- 方案要能穷尽职责边界：每个角色的输入/输出契约清晰，主程序不靠猜。

## 2. 第二步：按方案执行

### 2.0 方案进场三查（调度任何角色之前，必须先做）

拿到架构师方案后，主程序**在调度第一个 `Agent` 之前**，先做三项检查，任一不过就按对应规则停：

1. **缺角色**：`missing_roles` 非空 → 走 3.4「角色缺失硬退出」，**不调度任何角色**。
2. **角色名合法**：每个 `steps[].role` 都必须存在于角色清单；出现清单外的名字 → 走 3.2「退回架构师重设计」（算一次结构错误）。
3. **循环参数合法**：`loop.enabled == true` 的步骤，其 `max_rounds` 必须 ≥ 2；否则按字段约定补 3，或若为空/非法 → 同样退回架构师（算一次结构错误）。

三项全过，才进入 2.1 拓扑排序。

### 2.1 拓扑排序确定执行序

- 读方案里的 `steps` 和 `depends_on`，理清执行次序。
- **无依赖的步骤**：在同一条消息里发多个 `Agent` 调用，并发执行。
- **有依赖的步骤**：等上游返回后，把上游产出作为 `input` 喂给下游，再串行发起。

### 2.2 循环的执行

当某个步骤 `loop.enabled == true`：

1. 按步进执行：跑第一轮 → 拿到产出 → 对照 `converge_when` 判断是否收敛。
2. 未收敛且 `round < max_rounds`：把上一轮产出（含双方论点/新证据）作为输入，发起下一轮。
3. 收敛 或 `round >= max_rounds`：强制停止，取「当前最优」作为该步骤产出，并在成品里备注（若因触顶停止）「本循环在第 N 轮触上限收敛」。

> ⚠️ 主程序只负责「按上限跑」，不负责「反思该不该改方向」——那是架构师在方案里已经定好的。主程序不做任何方案外的自我纠错。

### 2.3 汇总裁决

- 按方案的 `merge` 策略汇总所有步骤产出。
- 若方案指定了 `final_role`（成品生成角色），**优先调起它**基于中间产出收口成成品，而非主程序内联拼凑。
- 最终输出必须是**用户要的实际成品**（报告 / 方案 / 代码 / 文章），不是编排过程说明。

## 3. 异常处理

### 3.1 区分两类错误：决定「退回重设计」还是「就地兜底」

不是所有失败都要推翻方案重来。先把错误归到两类：

| 类型 | 判据 | 处置 |
|---|---|---|
| **方案结构错误** | 拓扑依赖写错（上游没跑下游就依赖）、选的角色干不了这步、`converge_when` 永远无法满足、步骤间数据契约对不上 | **退回架构师重设计**（见 3.2） |
| **步骤执行错误** | 某个角色超时/返回垃圾/工具报错、某个具体取数失败（如表无权限） | **就地兜底/重试**，不推翻整个方案 |

判据口诀：「改执行方式也没用、得改 DAG 本身」→ 方案结构错误，退回架构师；「换个人重跑这步就行」→ 步骤执行错误，就地兜底。**只为一个叶子节点失败就让架构师重画整张 DAG 是浪费**，不要这么做。

### 3.2 退回架构师重设计（最多 5 次）

当判定为「方案结构错误」时，退回 `engineering-multi-agent-systems-architect` 重新设计：

- **退回时必带上下文**（不带全架构师重设计还是错）：
  - 失败发生在哪一步、失败现象是什么；
  - 哪些步骤已经成功跑完、其产出是什么；
  - 当前卡在哪个依赖或契约上。
- **重设计后**：按新方案的 `resume_from` 决定——填了步骤 `id` 则从该步骤（含已产出）续跑，缺省则从头重跑。
- **次数上限**：每次结构错误退回，累计 **最多 5 次**。第 5 次后仍失败，停止退回，如实交付「当前最优 + 失败说明 + 未及修正的缺口」，绝不无限重设计。计数器在此次 `/compose` 运行内全程累计，不清零。
- **额度边界**：**角色缺失导致的硬退出（3.4）不计入这 5 次额度**——缺角色是"原料不足"，退回重设计也变不出不存在的角色，退了无用。5 次额度只用于「角色都在、但图纸画错」的结构错误。

### 3.3 就地兜底（针对步骤执行错误）

- 若该步骤的 `fallback` 非空，按其中声明的兜底链（主路径 → 收窄兜底 → 降级/规则 → 人工）逐级降级处理，不退回架构师。
- `fallback` 留空时，该步骤最多重试 1 次；仍失败则停止该分支，在成品里如实交代「某步骤失败、结论缺失」。

### 3.4 其余

- **角色缺失（硬退出，不运行）**：若架构师方案里 `missing_roles` 非空（即有任务需要的角色、但角色库没有），主程序**立即停止、不调度任何角色去运行**，明确列出缺失的角色名与缺失原因（取自 `missing_roles`）。只有当这些角色被**补进角色清单**、架构师重新产出 `missing_roles` 为空的方案后，才允许继续运行。绝不猜测替代、绝不硬跑一个明知凑不齐角色的方案。
- **需求与角色清单严重不匹配**：如实告知，不硬编角色。
- **循环触顶仍未收敛**：如实标注，不粉饰。

## 4. 输出规范

最终只输出成品的实际内容。禁止输出「我设计了这样的方案」「我调了哪些角色」之类的编排过程（除非用户明确要求看方案）。

若执行中留下未竟事项（某步骤失败、循环触顶未收敛、某些假设未验证），在成品末尾附「遗留缺口」小节如实说明。

---

## 5. 运行留痕（每次任务存档到 cases/）

每次 `/compose` 运行，无论成败，都必须把**过程数据**落盘保存，供事后 review。这是不可跳过的硬性步骤。

### 5.1 存档目录

每个任务建一个子文件夹，命名 `<任务名>-YYYYMMDD-HHMMSS`（任务名取用户需求的前几个关键词，转成安全文件名；时间戳取开始时刻）：

```
cases/
└── <任务名>-时间戳/
    ├── 00-总览.md           # 人先看的导航锚点（见 5.3）
    ├── 10-DAG方案.json       # 架构师产出的完整方案（原样，结构错误重设计时存档最新一版）
    ├── 20-执行日志.md        # 每一步的流水记录（见 5.4）
    ├── 30-步骤产出/          # 每步原始产出，按 order 编号命名
    │   ├── S1-检索知识.md
    │   ├── S2-验证点.json
    │   └── ...
    ├── 40-代码与结果/        # 代码 + 紧邻它的执行结果（见 5.5）
    │   ├── <取数脚本>.py
    │   └── <取数脚本>-运行结果.txt
    ├── 50-最终报告.md        # 最终成品
    └── 90-遗留与偏差.md      # 未竟事项、失败、退回重设计记录（若有）
```

### 5.2 存档时机

- **开工即建目录**：拿到架构师方案的瞬间就建 `cases/<任务名>-时间戳/`，写 `00-总览.md` 骨架。中途任何一步失败，已产出的部分也要落盘——不能等全跑完才存，否则中途崩溃就全丢。
- **每步完成即写**：每个步骤（含循环的每一轮）完成后，立即把该步产出写入 `30-步骤产出/`，在 `20-执行日志.md` 追加一条记录。不要攒到最后一次写。
- **代码执行即留**：取数/计算代码写入 `40-代码与结果/`，执行后的 stdout/stderr 原文紧跟着存同名 `.txt`。

### 5.3 `00-总览.md`（阅读锚点，最重要）

这是人类 review 的入口，必须一眼看全「整体框架 + 流程 + 细节」，内容包含：

```markdown
# <任务名>

- **目标**：用户原始需求（原样）
- **结论**：最终 verdict / 关键论断（一行）
- **任务形状**：一次性 DAG / 含循环 DAG
- **起止时间 / 共多少步 / 成功几步失败几步**

## DAG 图（Mermaid）
[把 10-DAG方案.json 里的 topology 画成 mermaid flowchart]

## 文件导航表
| 环节 | 文件 |
|------|------|
| 检索 → 拆解 → 取数 → 研判 → 报告 | 30-步骤产出/S1..S7 + 40-代码与结果 + 50-最终报告 |

一句话说明「人该怎么读」：先看这个文件，再顺着导航表从上到下点开。
```

### 5.4 `20-执行日志.md`（流水线，可追溯）

每条记录含：步骤 id / 角色 / 输入来源 / 产出文件路径 / 状态（success|partial|escalated）/ 循环第几轮 / 耗时 / 关键结论或报错。目标：「任何一句最终结论，都能顺着执行日志回溯到产生它的那一格产出」。

### 5.5 代码与结果紧邻存放（解决"四处找对应"）

任何步骤产生代码（SQL/pyodps/Python），都必须同时保存：

- **代码本身**：`40-代码与结果/<描述名>.<ext>`
- **它的执行产物**：同一目录下紧邻的 `<描述名>-运行结果.txt`（含 stdout + stderr 原文）

**禁止**把代码和它的运行结果分开放到大目录堆里。人看一个脚本，旁边就是它的输出，不需要左右跳。

### 5.6 归档原则

- 文件名、目录名一律用**人类可读的中文描述 + 英文/数字编号**，不堆乱码。
- 敏感信息（AK 明文、真实手机号等）在落盘前脱敏——写"<redacted>"，禁止把 `.env` 的明文搬进 cases。
- `90-遗留与偏差.md` 只记「未竟事项、失败、退回重设计、数据缺口」，与最终报告里的"遗留缺口"呼应，但更细（含报错原文、SQL 全文）。

### 5.7 与 .workboard 的关系

`cases/` 是**持久、可复盘**的存档；`.workboard/` 是**单次运行过程**的临时草稿。运行结束后，把 cases 目录整理齐全即可，无需再维护 workboard。历史遗留的零散脚本（probe_/verify_ 系列）不在本机制内，不迁移。
