# 多智能体编排（架构师设计 → 主程序执行）

你扮演「统帅」，`engineering-multi-agent-systems-architect` 扮演「军师」。

整个流程只有两步：

1. **设计**：调架构师，把用户问题 + 全部可用角色清单交给它，让它产出**一份结构化、可直接执行的编排方案**。方案描述的是一个**有向图**——节点是步骤（角色），边是数据/控制流向。这个图**允许环（循环）**，但每条环都必须声明**硬轮次上限 `max_rounds`**。三种环形态：下游要求上游重取数/修正（`backedge`）、两个相反立场的角色互相辩论取证（`debate`）、单角色反复迭代（`self`）。
2. **执行**：主程序（你）严格按这份方案，用 `Agent` 工具真实调度角色，串行/并行/按设计的轮次上限跑，最后汇总裁决出成品。

架构师**只设计、不执行**；主程序**只执行、不设计**。二者职责不越界。

---

## 0. 三条不变的原则

1. **架构师定架构**：选哪个角色、什么拓扑、哪里需要回路（回退/辩论/自迭代）、回路几轮、怎么收敛——都是架构师在方案里写死的。主程序不擅自改结构。
2. **主程序定执行**：真实调起每个角色、把上游产出喂给下游、按方案声明的回路上限强制收敛。主程序不擅自加角色、不改循环次数。
3. **循环必有硬上限**：任何环（回退 / 辩论 / 自迭代）都必须在方案里写清 `max_rounds` 和 `收敛条件`。主程序跑满上限即强制停止——宁可在成品里诚实交代「未收敛」，也不死循环。

## 1. 第一步：读角色清单 + 调架构师

### 1.1 读预分组角色索引 + 一致性自检（只备料，不做选角）

**先从预分组索引读角色**：用 Read 读 `.claude/agent-index.md`（这是一份**预先按「任务职能」分好组**的静态角色索引，`name -> 中文名 + 一句话侧重点`），拿到当前所有可调度角色的名字与职能分组。

**再做一致性自检**（防止索引与 manifest 漂移）：运行一次脚本，确认索引里收录的角色名与 `agent-manifest.json` 完全一致：

```
python3 .claude/scripts/check-agent-index.py
```

- **自检通过（exit 0）**：照常往下走。
- **自检不通过（exit 1）**：说明索引与 manifest 已不同步（有角色新增未同步、或角色已删）。此时**停止选角**，把脚本输出的差异清单原样转告用户，提示「需要先同步 `agent-index.md` 与 `agent-manifest.json`」，不要带病运行——否则会把过期的角色清单喂给架构师。

**主程序不选角，只把「完整索引 + 取证路径」交给架构师**：

- 主程序把 `agent-index.md` **里除「附：非角色项」之外的全部分组**原样交给架构师（不替架构师按领域先筛一遍——筛是架构师的职责，见 1.2）。
- 同时告诉架构师两处可以深挖角色细节的取证位置：
  - `agent-manifest.json`：每条角色含 `name / role_path / category / cn_name / desc`；`desc` 是紧凑一句话。
  - `.claude/agents/<role_path>.md`：角色的**完整定义文件**，frontmatter 里的 `description` 与正文人设是判断「该角色到底能干什么」的最终依据。
- **禁止**把 `agent-index.md` 末尾「附：非角色项」里所列的各项（QUICKSTART、handoff-templates、phase-*、scenario-* 等）当作可选角色喂给架构师——它们是内部运营文档/流程模板，不是可调度角色。

选角完全交给架构师（见 1.2），主程序不预设任何「选谁」「缺谁」的结论。

### 1.2 调架构师设计（必须真实调起，不得内联）

调起：

```
Agent(subagent_type='engineering-multi-agent-systems-architect', prompt=...)
```

给架构师的 prompt 必须包含：

- **用户需求**：原样转述，不添油加醋。
- **角色索引（完整）**：`agent-index.md` 里除「附：非角色项」之外的全部分组（`name -> 中文名 + 一句话`），主程序不预筛，全部交给架构师。
- **取证路径**：`agent-manifest.json`（含 `desc`）与 `.claude/agents/<role_path>.md`（含 `description` 与正文人设）两处，供架构师深挖角色细节。
- **选角要求（架构师自己两步选角，不得略过）**：
  1. **初筛**：对照 `agent-index.md` 的任务职能分组，按用户需求涉及的领域，圈出可能相关的分组、并从中挑出候选角色集合。
  2. **定选**：对初筛出的每个候选角色，**细读它在 `agent-manifest.json` 里的 `desc`，以及 `.claude/agents/<role_path>.md` 里的 `description` 和正文人设**，据此判断它是否真的胜任该步骤，最终确定选用哪些角色。能力相近的角色（如同一分组里几个财务类角色）必须靠这一步的细读来区分，不能只凭一句话侧重点猜。
- **输出要求**：让架构师产出一份结构化方案，字段如下（用 JSON 或严格分节均可，主程序要能机器化读懂）：

```jsonc
{
  "topology": "说明整体拓扑（如 Router → 3 并行 → Synthesizer，或含 evaluator-optimizer 循环、下游回退上游、多空辩论）",
  "steps": [
    {
      "id": "步骤唯一标识",
      "role": "subagent_type（必须来自清单，不得编造）",
      "input": "此步骤的输入（写明上游哪个步骤的产出、或用户原始需求）",
      "output": "明确要求的输出格式（文本 / JSON / 列表，含关键字段）",
      "depends_on": ["依赖的步骤 id 列表（有向图的正常前向边，无则空）"],
      "fallback": "可选：本步骤失败时的兜底（主路径→收窄兜底→降级/规则→人工），无则留空",
      "loop": {
        "enabled": false,
        "mode": "self | debate | backedge",
        "group": "回路标识（可选，建议填）：同一组回路的步骤共用同一个短字符串 id，用于区分一个方案里的多个独立回路；单回路可省略",
        "max_rounds": 3,
        "converge_when": "收敛判据（仅 mode=self / debate 使用：如「证据不再新增」「立场连续2轮不变」；mode=backedge 不填，由 fix + max_rounds 终止）",
        "partners": ["参与本回路的其它步骤 id：debate=参与对立的全部步骤 id（含本步骤自身，若它下场辩论）；backedge=被回退的目标步骤 id（如取数步骤）；self=留空"],
        "affected_downstream": ["仅 mode=backedge 使用：回退上游重跑后，需要串行重跑的受影响下游步骤 id 列表（含本步骤），供主程序照单重跑、执行日志据实记录，不靠运行时推断"],
        "fix": "mode=backedge：下游要求上游修什么（如「换时间窗重取」「修正口径」）；mode=self：本轮相对上轮要改什么；mode=debate：留空"
      }
    }
  ],
  "merge": "最终如何汇总各步骤产出为成品（投票/加权/拼接/指定某一角色综合）",
  "final_role": "可选：指定一个成品生成角色（如 specialized-report-structurer）来收口；若某 debate 回路需要单独仲裁方（本步骤不下场辩论、只裁决），亦由 final_role 兼任，或在对应 step 的 output 里写明由谁裁决",
  "resume_from": "可选：退回重设计后，从哪个已成功的步骤续跑；缺省=从头重跑。注意：结构重设计后步骤 id 可能变化，主程序以「新方案」里的 id 为准重新解析，找不到则视为从头重跑",
  "missing_roles": [
    {
      "role": "任务需要但在角色清单里找不到的角色名",
      "type": "feasibility（可行性缺口，无法兜底）| quality（质量缺口，已降级兜底，仅为说明）",
      "reason": "为什么这一步必须有它、清单里的现有角色为何无法替代；quality 型须写明已用哪个现有角色降级兜底"
    }
  ]
}
```

> **字段约定**（主程序与架构师共同遵守）：
> - `depends_on` 表达的是图的**正常前向边**（数据流）。回退流、辩论流**不是** `depends_on`——它们用 `loop` 表达（见下）。
> - `loop.enabled == true` 时，`max_rounds` **必须 ≥ 2**（缺省按 3 处理）；`enabled == false` 时 `loop` 其余字段忽略。
> - `loop.mode` 三选一：
>   - `self`：单个角色反复迭代（假设更新-再验证）。`partners` 可空。
>   - `debate`：两个（或多个）立场对立的角色轮流发言、取证、修正。`partners` 列出**参与对立的全部**步骤 `id`（含本步骤自身，若本步骤也要下场辩论）；若本步骤**只作仲裁方不下场**，则 `partners` 不含本步骤，仲裁由 `final_role` 兼任（见 schema）。多个 `debate` 步骤指向同一组 `partners` 时，视为**同一个辩论回路**，共用一个 `max_rounds` 计数器。
>   - `backedge`：下游完成后发现上游产出有问题，**回退要求上游重取数/修正**。`partners` 填被回退的目标步骤 `id`（如取数步骤）；`fix` 写清要修什么；`affected_downstream` 显式列出「回退后需要串行重跑的受影响下游步骤 `id` 集合（含本步骤）」，让主程序照单重跑、执行日志据实记录，不靠运行时推断（否则回退到底重跑了哪些下游、是否漏了某个下游，事后 review 无从核对）。回退边不改变图的骨架，只是形成一条受 `max_rounds` 约束的回边。
> - `loop.group`（可选）：同一组回路（同一组 `debate` 的 `partners`、或同一 `backedge` 的目标+受影响下游）里的所有步骤应填**同一个**短字符串 `group`。它的作用是让「一个方案里存在多个独立回路」时能彼此区分——默认一个方案只有一组回路，此时可省略；一旦出现两组以上互不相干的辩论/回退，必须用 `group` 区分，否则主程序与可视化会把它们混成一团。
> - `resume_from` 缺省（空）＝退回后**从头重跑**；若填了某步骤 `id`，则从该步骤（含其下游）续跑，该步骤之前的产出保留不动（语义以 3.2 为准）。
> - `fallback` 留空＝该步骤无兜底，失败按 3.3 的「重试 1 次」处理。

**关键约束**（写进 prompt，让架构师遵守）：

- 角色 `name` 必须来自角色索引（最终以 `agent-manifest.json` 里的真实角色名为准），禁止编造。
- **避开废弃角色（deprecated）**：`agent-manifest.json` 里带 `deprecated` 字段的角色，是「已被某个现役角色取代」的同义重复角色；`agent-index.md` 里它们也被标了「【已废弃，见 X】」。架构师选角时**不得**选用带 `deprecated` 标记的角色——应直接选用它 `deprecated` 字段指向的那个现役角色。废弃角色仍在 manifest 里只是为了向后兼容、不引发索引漂移，不是可选项目。
- **角色可行性前置校验（两步选角后报缺，不得硬凑）**：架构师在产方案前，先按「初筛分组 → 细读 `desc`/`description` 定选」两步走完，再逐步核对「这步要干的活，清单里有没有角色能胜任」。若某步在清单里**找不到胜任角色**，架构师**不得**瞎挑一个名字相近的角色硬顶，也不得虚构一个不存在的角色——而是把它填进方案的 `missing_roles` 数组，并写明「为什么必须有它、现有角色为何无法替代」。
- **区分「可行性缺口」与「质量缺口」，缺领域专家 ≠ 缺角色**：这是判断某角色是否报入 `missing_roles` 的核心判据——
  - **可行性缺口（报入 `missing_roles`）**：没有这个角色，该步骤**完全无法产出可交付的结果**。判据词是「跑不了」，而非「跑不深」。典型场景：必须依赖某种不可由通用检索还原的封闭知识/仿真/资质（如军工保密体制内情、需逐步解的工程仿真），通用角色 + 联网检索也无法产出诚实可用的结果。
  - **质量缺口（不报 `missing_roles`，写成 `fallback` + output 标注）**：通用角色 + 联网检索能产出「框架完整、专业深度打折」的结果，只是达不到领域专家的深度。这类缺口是「跑不深」，不是「跑不了」——架构师**不得**因此报入 `missing_roles`。正确处置是：选用能力最接近的通用角色，在其 `fallback` 里写明「降级为通用检索兜底」，并在 `output` 契约里**显式要求标注「该维度专业深度不足 / 置信度打折」**，把短板交给下游成稿角色如实呈现。
  - 判据口诀：**「换通用角色 + 联网检索，还能不能交付一份诚实可用的结果？」能 → 质量缺口，降级兜底；不能 → 可行性缺口，报 `missing_roles`。** 行业分析、趋势研究、政策综述这类「公开事实 + 可检索」的任务，几乎都是质量缺口，不应报缺。
- 需要「对抗校验 / 辩论」时，架构师**自建辩论者循环**（`loop.mode = "debate"`，让对立角色互攻），而非依赖任何固定存在的元角色；需要「上游重取数 / 修正」时用 `loop.mode = "backedge"`。三种 `mode` 的字段语义见上文字段约定。
- **字段翻译桥（重要）**：你熟悉的拓扑模式里的回边，要落到本方案的具体字段上——evaluator-optimizer 的「`[fail + feedback]` 回 Generator」、层级式的「`feedback` 边」、mesh 的「agent 互连」分别对应本方案的 `loop.mode = backedge / debate`；把「谁回退到谁」填进 `partners`、「回退要修什么 / 辩论哪两方对立」填进 `fix` 或 `partners`。不要只在 `topology` 里用文字描述回边，而不落到 `loop` 字段。
- 方案要能穷尽职责边界：每个角色的输入/输出契约清晰，主程序不靠猜。

## 2. 第二步：按方案执行

> **需求含糊时的默认策略**：若用户需求对「地域 / 时间窗 / 深度 / 受众」等未指明，**采用合理默认值继续跑，不中途打断用户追问**（例：行业分析默认「全球+中国、近 1 年、管理层受众、全维度」）。若架构师方案里带出了 `clarifications` 字段（认为必须澄清才可执行），主程序才停下来向用户确认——其余情况一律默认值推进，并把采用的默认值写进 `00-总览.md` 的「目标」栏供回溯。

### 2.0 方案进场检查（调度任何角色之前，必须先做）

拿到架构师方案后，主程序**在调度第一个 `Agent` 之前**，先做以下检查，任一不过就按对应规则停：

1. **缺角色（分两类处置）**：
   - `missing_roles` 中**存在 `type == "feasibility"` 的项**（可行性缺口）→ 走 3.4「角色缺失硬退出」，不调度任何角色。
   - `missing_roles` **仅含 `type == "quality"` 的项**（质量缺口，架构师已在对应 step 的 `fallback` 里声明降级兜底）→ **不阻断**，照常进入 2.1 执行；主程序只需在成品「遗留缺口」里如实交代这些专业深度受限的维度（取自 `missing_roles` 的 `reason`）。
   - `missing_roles` 非空但 `type` 未标注 → 视为 `feasibility` 处理（从严），走 3.4。
2. **角色名合法**：每个 `steps[].role` 都必须存在于 `agent-manifest.json` 的**真实角色名集合**（排除 `strategy` 目录 16 项 NON_ROLE_NAMES）；出现清单外的名字 → 走 3.2「退回架构师重设计」（算一次结构错误）。注意：**合法基准是 manifest 全量角色，不是「喂给架构师的相关分组」**——相关分组只是提示，架构师若选了一个不在相关分组、但确实在 manifest 里的角色，是合法的，不得误判。
3. **循环参数合法**：`loop.enabled == true` 的步骤，其 `max_rounds` 必须 ≥ 2；且 `mode` 必须是 `self` / `debate` / `backedge` 之一。`mode = "debate"` 或 `"backedge"` 时 `partners` 必须非空且指向真实存在的步骤 `id`。任一项不合法 → 补缺省值，或若为空/非法到无法补救 → 退回架构师（算一次结构错误）。
   - **debate 计数器一致性（补充校验）**：所有声明了 `mode = "debate"` 的步骤，其 `partners` 集合必须**完全一致**（同一组辩论回路的步骤指向同一组对立 `partners`）。若出现两处 debate 步骤的 `partners` 不一致，意味着架构师画出了两个不同的辩论回路，主程序无法判断是否共用一个 `max_rounds` 计数器——此时退回架构师重设计（算一次结构错误），而非在执行阶段才陷入歧义。
4. **final_role 合法**：若方案的 `final_role` 非空且不在 `steps[].role` 里，同样须通过「角色名合法」校验（基准同上：manifest 真实角色名集合）——否则 2.3 会去调一个未经校验的角色。

四项全过，才进入 2.1 确定执行序。

### 2.1 确定执行序（前向依赖序为主，回路由 2.2 单独处理）

- 读方案里的 `steps` 和 `depends_on`，理清执行次序。
- **无依赖的步骤**：在同一条消息里发多个 `Agent` 调用，并发执行。
- **有依赖的步骤**：等上游返回后，把上游产出作为 `input` 喂给下游，再串行发起。
- `loop.mode = "backedge"` 的回退边、`debate` 的攻防边**不计入 `depends_on` 的前向执行序**——它们不是前向数据流，而是由 2.2 统一管理的有上限回路。先按 `depends_on` 把前向骨架跑起来，回退/辩论在 2.2 里触发。

### 2.2 回路的执行（含回退边、辩论者循环、自循环）

凡 `loop.enabled == true` 的步骤（或一组指向同一回路的步骤），按 `mode` 分三种执行方式，但**共同遵守一条铁律：回路有硬轮次上限 `max_rounds`，主程序只数轮次、触顶即停，不判断「该不该继续」。**

1. **`self`（自循环，单角色反复迭代）**：
   - 跑第一轮 → 拿产出 → 对照 `converge_when` 判断是否收敛。
   - 未收敛且 `round < max_rounds`：把上一轮产出作为输入，发起下一轮。
   - 收敛 或 `round >= max_rounds`：强制停止，取「当前最优」作为该步骤产出。

2. **`debate`（辩论者循环，多方互相攻防）**：
   - 把所有 `partners` 里的角色都调起（可并行），各自从己方立场产出第一轮论点 + 取证。
   - 把各方的论点/证据**汇总后交叉喂回**（A 看到 B 的论据、B 看到 A 的论据），发起下一轮；每一轮各方可在上一轮基础上调整立场、补充或修正证据。
   - 对照 `converge_when` 判断是否收敛（如：双方证据不再新增、立场连续两轮无实质变化）；未收敛且 `round < max_rounds` 继续，否则强制停止。停止后，若方案指定了仲裁/收口角色，调起它基于双方最终论据裁决；否则主程序按 `merge` 策略取各方最优。
   - **注意**：一组 `debate` 步骤若指向同一组 `partners`，它们共用**同一个轮次计数器**（一次「A 说 + B 说」算一轮），不要把每个角色各自单独计数导致轮次翻倍。

3. **`backedge`（回退边，下游要求上游重取数/修正）**：
   - 当本步骤（下游）产出后发现上游产出不合格（缺数、口径错、时间窗不符等），按 `fix` 写明的修法，**回退触发 `partners` 指向的上游步骤重跑**（如重新取数）。
   - 上游重跑后，其所有受影响的**下游**串行重跑一遍。**受影响下游的范围以本步骤 `loop.affected_downstream` 显式列出的步骤 `id` 为准**（缺省视为仅含本步骤自身）；主程序照单重跑，并在执行日志里逐条记录「回退触发了哪些下游重跑」，而非靠运行时临时推断。
   - 回退计入 `max_rounds`：每「回退上游并重跑受影响下游」一次算一轮；达到 `max_rounds` 仍未满足，强制停止，采用当前产出并在成品里如实交代「上游数据经 N 轮修正仍未达标」。

> ⚠️ 主程序只负责「按上限跑」，不负责「反思该不该改方向」——回路怎么收敛、回退要修什么、辩论到何种程度停，都是架构师在方案里已写死的。主程序不做任何方案外的自我纠错，也不主动新增或延长回路。

### 2.3 汇总裁决

- 按方案的 `merge` 策略汇总所有步骤产出。
- 若方案指定了 `final_role`（成品生成角色），**优先调起它**基于中间产出收口成成品，而非主程序内联拼凑。
- 最终输出必须是**用户要的实际成品**（报告 / 方案 / 代码 / 文章），不是编排过程说明。

## 3. 异常处理

### 3.1 区分两类错误：决定「退回重设计」还是「就地兜底」

不是所有失败都要推翻方案重来。先把错误归到两类：

| 类型 | 判据 | 处置 |
|---|---|---|
| **方案结构错误** | 依赖关系写错（上游没跑下游就依赖）、选的角色干不了这步、`converge_when` 永远无法满足、步骤间数据契约对不上、回路的 `partners`/回退目标指向不存在的步骤 | **退回架构师重设计**（见 3.2） |
| **步骤执行错误** | 某个角色超时/返回垃圾/工具报错、某个具体取数失败（如表无权限） | **就地兜底/重试**，不推翻整个方案 |

判据口诀：「改执行方式也没用、得改图本身」→ 方案结构错误，退回架构师；「换个人重跑这步就行」→ 步骤执行错误，就地兜底。**只为一个叶子节点失败就让架构师重画整张图是浪费**，不要这么做。

### 3.2 退回架构师重设计（最多 5 次）

当判定为「方案结构错误」时，退回 `engineering-multi-agent-systems-architect` 重新设计：

- **退回时必带上下文**（不带全架构师重设计还是错）：
  - 失败发生在哪一步、失败现象是什么；
  - 哪些步骤已经成功跑完、其产出是什么；
  - 当前卡在哪个依赖或契约上。
- **重设计后**：按新方案的 `resume_from` 决定——填了步骤 `id` 则从该步骤开始逐步往下重跑（`resume_from` 之前的步骤产出**保留不动**，`resume_from` 这一步及其所有**下游**依赖步骤重新执行）；缺省（空）则从头重跑全部。**注意**：重设计会改变图，`resume_from` 里的旧步骤 `id` 可能已不存在，主程序以**新方案**的 `id` 为准重新解析，找不到则视为从头重跑。
- **次数上限**：每次结构错误退回，累计 **最多 5 次**。第 5 次后仍失败，停止退回，如实交付「当前最优 + 失败说明 + 未及修正的缺口」，绝不无限重设计。计数器在此次 `/compose` 运行内全程累计，不清零。
- **额度边界**：**角色缺失导致的硬退出（3.4）不计入这 5 次额度**——缺角色是"原料不足"，退回重设计也变不出不存在的角色，退了无用。5 次额度只用于「角色都在、但图纸画错」的结构错误。

### 3.3 就地兜底（针对步骤执行错误）

- 若该步骤的 `fallback` 非空，按其中声明的兜底链（主路径 → 收窄兜底 → 降级/规则 → 人工）逐级降级处理，不退回架构师。
- `fallback` 留空时，该步骤最多重试 1 次（重试时**可换一个清单内角色**重跑，不必拘泥原角色——这正是 3.1 口诀里「换个人重跑这步就行」的含义）；仍失败则停止该分支，在成品里如实交代「某步骤失败、结论缺失」。

### 3.4 其余

- **角色缺失（硬退出，不运行）**：仅当架构师方案的 `missing_roles` 里存在 `type == "feasibility"`（可行性缺口，无法兜底）的项时，主程序**立即停止、不调度任何角色去运行**，明确列出缺失的角色名与缺失原因（取自 `missing_roles`）。只有当这些角色被**补进角色清单**、架构师重新产出无 feasibility 缺口的方案后，才允许继续运行。绝不猜测替代、绝不硬跑一个明知凑不齐角色的方案。若 `missing_roles` 仅含 `quality` 型（质量缺口），**不硬退**，按 2.0 第 1 点的降级路径继续，缺口在成品「遗留缺口」交代。
- **需求与角色清单严重不匹配**：如实告知，不硬编角色。
- **循环触顶仍未收敛**：如实标注，不粉饰。

---

## 4. 输出规范

最终只输出成品的实际内容。禁止输出「我设计了这样的方案」「我调了哪些角色」之类的编排过程（除非用户明确要求看方案）。

若执行中留下未竟事项（某步骤失败、循环触顶未收敛、某些假设未验证），在成品末尾附「遗留缺口」小节如实说明。

## 5. 运行留痕（每次任务存档到 cases/）

每次 `/compose` 运行，无论成败，都必须把**过程数据**落盘保存，供事后 review。这是不可跳过的硬性步骤。

### 5.1 存档目录

每个任务建一个子文件夹，命名 `<任务名>-YYYYMMDD-HHMMSS`（任务名取用户需求的前几个关键词，转成安全文件名；时间戳取开始时刻）：

```
cases/
└── <任务名>-时间戳/
    ├── 00-总览.md           # 人先看的导航锚点（见 5.3）
    ├── 10-DAG方案.json       # 架构师产出的完整方案（原样存档，结构错误重设计时存最新一版；文件名沿用历史约定，内容实为「含回路的方案」）
    ├── 20-执行日志.md        # 每一步的流水记录（见 5.4）
    ├── 30-步骤产出/          # 每步原始产出，按 order 编号命名
    │   ├── S1-检索知识.md
    │   ├── S2-验证点.json
    │   └── ...
    ├── 40-代码与结果/        # 代码 + 紧邻它的执行结果，合并在同一个文件（见 5.5）
    │   └── <取数脚本>.md      # 一个脚本一个文件，内含「代码块 + 运行结果块」上下对应
    ├── 50-最终报告.md        # 最终成品
    └── 90-遗留与偏差.md      # 未竟事项、失败、退回重设计记录（若有）
```

### 5.2 存档时机

- **开工即建目录**：拿到架构师方案的瞬间就建 `cases/<任务名>-时间戳/`，写 `00-总览.md` 骨架。中途任何一步失败，已产出的部分也要落盘——不能等全跑完才存，否则中途崩溃就全丢。
- **每步完成即写**：每个步骤（含循环的每一轮）完成后，立即把该步产出写入 `30-步骤产出/`，在 `20-执行日志.md` 追加一条记录。不要攒到最后一次写。
- **代码执行即留**：取数/计算代码写入 `40-代码与结果/`，执行后的 stdout/stderr 原文**紧跟着写进同一文件**（见 5.5）。

### 5.3 `00-总览.md`（阅读锚点，最重要）

这是人类 review 的入口，必须一眼看全「整体框架 + 流程 + 细节」，内容包含：

```markdown
# <任务名>

- **目标**：用户原始需求（原样）
- **结论**：最终 verdict / 关键论断（一行）
- **任务形状**：一次性有向图 / 含回路有向图（回退 / 辩论 / 自迭代）
- **起止时间 / 共多少步 / 成功几步失败几步**

## 任务流程图（Mermaid）
[把 10-DAG方案.json 里的 topology + 回路 画成 mermaid flowchart，回退边/辩论边用不同样式的箭头标出（文件名沿用历史约定，内容实为「含回路的方案」）]

## 文件导航表
| 环节 | 文件 |
|------|------|
| 检索 → 拆解 → 取数 → 研判 → 报告 | 30-步骤产出/S1..S7 + 40-代码与结果 + 50-最终报告 |

一句话说明「人该怎么读」：先看这个文件，再顺着导航表从上到下点开。
```

### 5.4 `20-执行日志.md`（流水线，可追溯）

每条记录含：步骤 id / 角色 / 输入来源 / 产出文件路径 / 状态（success|partial|escalated）/ 循环第几轮 / 耗时 / 关键结论或报错。目标：「任何一句最终结论，都能顺着执行日志回溯到产生它的那一格产出」。

### 5.5 代码与结果合并存储（一脚本一文件，一一对应）

任何步骤产生代码（SQL/pyodps/Python），**代码和它的运行结果必须合并写入同一个文件**，一个脚本一个文件，上下对应，禁止拆成两个文件分开放。

文件：`40-代码与结果/<描述名>.md`，内部结构固定如下：

````markdown
# <描述名>

## 代码

```python
<完整、可复制的脚本/SQL 原文>
```

## 运行结果

```text
<stdout + stderr 原文，脱敏后>
```
````

要点：

- **一段代码 → 一段紧邻它的运行结果**，用「代码块 → 结果块」上下排列；一个脚本内部有多个查询/步骤时，就地按 `步骤1 代码 → 步骤1 结果 → 步骤2 代码 → 步骤2 结果` 依次展开，不让任何一段结果脱离它对应的代码。
- 代码块保留原文、可直接复制重跑；结果块是执行时的真实 stdout/stderr（脱敏后）。
- **禁止**把代码和它的运行结果拆成 `.py` 和 `.txt` 两个文件分开放。人看一个脚本文件，它的输入（代码）和输出（结果）就在同一个文件里上下对照，不需要左右跳。

### 5.6 归档原则

- 文件名、目录名一律用**人类可读的中文描述 + 英文/数字编号**，不堆乱码。
- 敏感信息（AK 明文、真实手机号等）在落盘前脱敏——写"<redacted>"，禁止把 `.env` 的明文搬进 cases。
- `90-遗留与偏差.md` 只记「未竟事项、失败、退回重设计、数据缺口」，与最终报告里的"遗留缺口"呼应，但更细（含报错原文、SQL 全文）。

### 5.7 与 .workboard 的关系

`cases/` 是**持久、可复盘**的存档；`.workboard/` 是**单次运行过程**的临时草稿。运行结束后，把 cases 目录整理齐全即可，无需再维护 workboard。历史遗留的零散脚本（probe_/verify_ 系列）不在本机制内，不迁移。
